# DAQEM Studios: Documentation Style Guide

This guide defines the standards for all documentation and wiki pages across DAQEM Studios projects. Our goal is to create a cohesive, professional, and highly readable experience for server administrators, modpack developers, and players.

## 1. Landing Pages (`index.mdx`)
Every project's landing page must follow a strict, predictable structure. Get straight to the point without using conversational "Welcome!" banners.

**Required Layout:**
1. **`<ProjectHeader />`**: Always at the very top. Handles the logo, title, description, and external links.
2. **Overview**: 1-2 short paragraphs explaining exactly what the mod does.
3. **Key Features**: A bulleted list or a grid of feature cards (`<div className="mc-card">`).
4. **Quick Links**: A standardized section pointing to Installation, Configuration, and core mechanics.

*Do not use `<Admonition>` blocks for greetings.*

## 2. Navigation & Sidebar Hierarchy
A unified sidebar structure ensures users instinctively know how to navigate any of our projects. Sidebars (`sidebar.ts`) and their corresponding file directories must follow a strict, standardized hierarchy.

### Standardized Category Breakdown
Every project must organize its documentation into these standardized top-level categories (omit categories that don't apply, such as API for a non-library mod):

1. 🚀 **Getting Started**
   * Must include: `Installation` and `Configuration`.
   * Optional: `Quick Start Guide`.
2. 🧩 **Core Mechanics / Features** 
   * The meat of the mod (e.g., "Player Actions" for GriefLogger, "Jobs" for Jobs+).
   * Group related pages into nested folders if there are more than 5 items.
3. 💻 **Commands & Permissions**
   * A dedicated section explaining admin/player commands, arguments, and permission nodes.
4. 📄 **JSON Formats** (If applicable)
   * For data-driven mods (Arc, Item Restrictions). Keep format schemas separate from tutorials.
5. 🛠️ **Development / API** (If applicable)
   * Instructions for other modders (Dependency Setup, Maven links, Event Hooks).

### Category Index Pages (`index.mdx`)
Every category (folder) **must** have an `index.mdx` file. 
* Do not leave category folders as unclickable dropdowns.
* The `index.mdx` file for a category must contain a brief sentence explaining the category, followed by the `<DocCardList className="category-list" />` component to automatically generate a grid of sub-pages.

### Expansion & Collapsing Rules
To prevent the sidebar from becoming overwhelmingly long (like in the Arc Lib docs) while keeping it discoverable:
* **Top-Level Categories:** Should be `collapsed: false` by default so users can see the main sections immediately.
* **Nested Categories (Sub-folders):** Must be `collapsed: true` by default.

### Emoji Policy
Emojis serve as quick visual anchors. To maintain a clean look:
* Use emojis **only** on top-level categories (e.g., "Getting Started", "Development").
* **Do not** use emojis on individual document pages or nested sub-categories to prevent visual clutter.
* **Standard Emojis to use:**
  * 🚀 Getting Started
  * 🎮 Player/Gameplay Mechanics
  * 🧩 Blocks/Items/Features
  * 💻 Commands & Permissions
  * 📄 JSON Formats / Data
  * 🛠️ Development / API

### Example `sidebar.ts` Implementation
Your `sidebar.ts` files must be configured explicitly. Avoid relying solely on `autogenerated` so you can strictly control order, emojis, and category links.

```typescript
import type { SidebarsConfig } from "@docusaurus/plugin-content-docs";

const sidebar: SidebarsConfig = {
    sidebar: [
        {
            type: "doc",
            id: "index",
            label: "Project Name", // Root landing page
        },
        {
            type: "category",
            label: "Wiki",
            items: [
                {
                    type: "category",
                    label: "Getting Started",
                    collapsed: false, // Top-level is open
                    customProps: { emoji: "🚀" },
                    link: { type: "doc", id: "wiki/getting-started/index" },
                    items: [
                        { type: "doc", id: "wiki/getting-started/installation", label: "Installation" },
                        { type: "doc", id: "wiki/getting-started/configuration", label: "Configuration" },
                    ],
                },
                {
                    type: "category",
                    label: "Features",
                    collapsed: false, // Top-level is open
                    customProps: { emoji: "🧩" },
                    link: { type: "doc", id: "wiki/features/index" },
                    items: [
                        // Sub-categories should be collapsed: true
                        {
                            type: "category",
                            label: "Advanced Systems",
                            collapsed: true, 
                            link: { type: "doc", id: "wiki/features/advanced/index" },
                            items: [
                                { type: "doc", id: "wiki/features/advanced/system-a" }
                            ]
                        }
                    ],
                },
            ],
        },
    ],
};

export default sidebar;
```

## 3. Admonitions (Callouts)
Use Docusaurus's markdown syntax (`:::`) for callouts. Reserve them strictly for technical context, not formatting or greetings.

* `:::note`: Minor, supplementary information.
* `:::tip`: Best practices or shortcuts.
* `:::info`: Neutral, technical context.
* `:::warning`: Actions that might negatively affect gameplay or confuse the user.
* `:::danger`: Actions that will crash the server, corrupt data, or cause massive lag.

## 4. Custom Components
Leverage our custom React components to make the wiki feel like a bespoke web app:
* **`<MinecraftItem />`**: Use whenever mentioning a specific vanilla or modded item.
* **`<RecipeGrid />`**: Use for all crafting tutorials.
* **`<DocCardList />`**: Use on all intermediate category pages (`index.mdx`) to generate automatic grid menus.
* **`<InfoBox />`**: Use for Wiki-style fact files (e.g., Job stats, farm tiers).

## 5. Tone of Voice
* **Professional & Direct:** Avoid conversational fluff. (e.g., Use *"GriefLogger is a server-side logging tool"*, not *"Welcome to the wiki for GriefLogger, your awesome new tool!"*).
* **Active Voice:** Use imperative verbs for instructions (e.g., *"Open the config file"*, not *"The config file should be opened"*).
* **Audience-Aware:** Speak directly to the server admin or developer. Assume basic technical knowledge, but thoroughly explain mod-specific terminology.

## 6. Global Support Pages
Do not duplicate Support, Discord, or Issue Reporting pages for every mod. 
Link directly to the global DAQEM Studios support pages located in `/docs/daqem/wiki/support/` to maintain a single point of update.
